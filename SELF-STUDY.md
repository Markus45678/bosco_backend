# Звіт з експериментів у ПР №2.5

Під час виконання лабораторної роботи я навмисно перевірив кілька типових помилок при роботі з шаблонами в Django і зафіксував результати.

---

### Експеримент 1: Що буде, якщо вказати шлях до шаблону без назви застосунку?
* **Що робив:** Написав у views.py `render(request, 'products.html')` замість `render(request, 'store/products.html')`.
* **Що сталося:** Django відразу видав помилку `TemplateDoesNotExist`.
* **Мій висновок:** Django очікує, що шаблони лежать у папці `templates/<app_name>/`. Якщо не робити цієї вкладеної папки з назвою застосунку, Django просто не зрозуміє, з якого саме додатку брати файл (і це захищає від ситуацій, коли у двох різних застосунках є файли з однаковою назвою).

---

### Експеримент 2: Спроба написати HTML поза блоками `{% block %}`
* **Що робив:** Додав кілька рядків звичайного HTML-коду у файлі `products.html` перед тегом `{% block content %}` і після `{% endblock %}`.
* **Що сталося:** Цей код взагалі не з'явився на сторінці в браузері.
* **Мій висновок:** Коли шаблон наслідує базовий через `{% extends "base.html" %}`, Django ігнорує все, що лежить поза межами офіційних блоків. Усі елементи сторінки треба обов'язково загортати у відповідні `{% block %}`.

---

### Експеримент 3: Додавання нових тегів без перезапуску сервера
* **Що робив:** Створив новий тег у файлі `store_extras.py` і відразу спробував використати його в HTML-шаблоні, не чіпаючи запущенний `runserver`.
* **Що сталося:** Отримав помилку `store_extras is not a registered tag library`.
* **Мій висновок:** Django зчитує вміст папки `templatetags` лише один раз під час старту. Якщо створювати нові файли тегів чи фільтрів, треба обов'язково зупиняти й заново запускати `python manage.py runserver`, інакше система їх не побачить.

### Експеримент 4: Відправка POST-форми без токена безпеки
* **Що робив:** Прибрав тег `{% csrf_token %}` з HTML-форми додавання товару та спробував відправити дані.
* **Що сталося:** Сервер повернув помилку `403 Forbidden` із повідомленням `CSRF verification failed`.
* **Мій висновок:** Django за замовчуванням блокує будь-які POST-запити без CSRF-токена, щоб захистити користувачів від крос-сайтових атак. Тег `{% csrf_token %}` є обов'язковим для кожної форми з методом POST.
